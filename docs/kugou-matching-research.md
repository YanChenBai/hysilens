# 酷狗本地歌词身份匹配调研

调研日期：2026-11-11。本文记录只读实机观察和建议，尚未改变应用匹配逻辑。数据库来自当前电脑，不能据此保证其他版本的结构或所有曲目的字段语义。

## 结论

建议优先验证“SMTC 完整元数据 → 数据库歌曲候选 → 音质 hash 关联 → LyricInfo → KRC 内容校验”。标题用于找候选，不作为最终歌曲身份。INI 是延迟写入的辅助信息；CDP 当前 hash / ID 是解决剩余歧义的可选增强来源。

仅有标题、歌手且存在多个不同录音时，数据库无法凭空恢复当前播放 ID。缓存中只有一个文件也不能排除当前播放的是另一个没有缓存的版本。

## 本机证据

数据库 `%APPDATA%/KuGou8/KGMusicV3.db` 为加密 SQLite。本次参考社区页解码算法，在内存中解码并使用 SQLite 只读查询，未修改原数据库，也未在仓库保存解码后的数据库。三份数据库快照的 `quick_check` 均通过；这不代表实时读取具有事务一致性。

相关表及用途：

| 表                      | 本次确认的相关字段                                                                                                                                        | 用途与限制                                                                             |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `PlayQueueAssistItem_0` | `SongName`, `TitleName`, `Singer`, `MusicFileAlbum`, `MixSongID`, `TrueMixSongID`, `MusicFileHash`, `OriginHash`, `LastPlayedMusicHash`, `RecommendKRCId` | 播放队列候选；不是当前播放指针，不能按最近一行或最大 ID 选歌                           |
| `MusicVersionsInfos`    | `MixSongID`, `SDHash`, `HDHash`, `PDHash`, `HiResHash`，以及各音质时长等                                                                                  | 同一记录下音质资源的关联依据；特殊音效/人声/伴奏资源应单独验证，不能一概认为时间轴相同 |
| `LyricInfo`             | `SongHash`, `KRCID`, `LyricPath`, `SongName`, `SingerNames`, `Duration`                                                                                   | 客户端记录的歌词路径；仍需检查关联和文件内容，时长可能为 0                             |
| `CompletionSongInfos`   | `MixSongID`, `Hash`, `AlbumID`, `AlbumName`, `TitleName`, `Duration`, `AudioID` 等                                                                        | 补充候选元数据；不能证明该行当前正在播放                                               |

一个包含 48 条队列记录的快照中，45 条 `LastPlayedMusicHash` 与 `MusicFileHash` 不同；其中 42 条能在对应 `MusicVersionsInfos` 行的 hash 字段中找到。记录包含重复歌曲，这不是去重歌曲数，也不是全库准确率。说明只比一个 hash 会漏掉大量本机记录，剩余 3 条不能擅自推定对应关系。

### Flower Dance 的实际歧义

| 标题                    | MixSongID   | 专辑                                                       | 数据库时长 |
| ----------------------- | ----------- | ---------------------------------------------------------- | ---------- |
| `Flower Dance`          | `104979032` | `A Cup Of Coffee`                                          | 263836 ms  |
| `Flower Dance`          | `28145635`  | `Libyus Music Sound History 2004-2010 Mixed by DJ OKAWARI` | 166974 ms  |
| `Flower Dance (花之舞)` | `170815922` | `Libyus Music Sound History 2004－2010`                    | 265848 ms  |

前两条标题和歌手相同，歌曲身份、专辑、时长不同，不能合并。第三条的 KRC 文件名和 `LyricInfo.SongHash` 使用 HD hash，KRC 内部 `[hash:]` 却使用 SD hash；`MusicVersionsInfos` 能解释这种差异，不能直接视作文件损坏。另一份 Flower Dance 的 KRC 内 `[hash:]` 为空、`[total:0]`，这些字段不能成为必填条件。

`RecommendKRCId=19525574` 出现在多条队列记录中，而本机 `LyricInfo` 中该 ID 对应 `Jamvana - OBA O`，不能把推荐歌词 ID 单独当作可靠关联键。这可能是旧值或其他客户端行为，原因尚未确认。

### SMTC 还有被当前实现忽略的信息

本次直接读取全部相关字段时得到：

```text
Title: Flower Dance (花之舞)
Artist: 空
AlbumTitle: 空
AlbumArtist: 《Libyus Music Sound History 2004－2010》
Subtitle: 空
TrackNumber / AlbumTrackCount: 0 / 0
Position / EndTime: 0 / 0
```

酷狗这次把类似专辑名的文本放在 `AlbumArtist`。当前公共采集代码只保留 `Title`、`Artist`、`AlbumTitle`，丢掉了这个线索。应先保留原始字段；只有酷狗适配器在验证格式和数据库候选后，将这种值作为专辑提示，不能全局把 AlbumArtist 当专辑名，更不能当歌手补齐。

此前连续 SMTC 采样捕获《痴心绝对 (R&B版)》、`Dancin (Krono Remix)`、`Flower Dance Pt.2`、`Flower Dance`、`Flower Dance (花之舞)`、陶喆《就是爱你》。Dancin 的 SMTC 歌手为空，仍可查到数据库歌曲和本地 KRC。Flower Dance Pt.2 首次查询没有记录、后续出现，且用户确认本来没有歌词：查不到歌词不等于歌曲识别失败。采样时间只有观察时间，没有用户点击时间，不能用来宣称端到端延迟。

## 建议的匹配规则

1. 切歌时产生新的查询代次。采集原始 SMTC 标题、歌手、专辑、AlbumArtist、Subtitle；空字段不继承上一首。标题发生变化立即撤销上一首自动匹配，异步结果必须与查询代次一致。
2. 按完整标题查数据库候选，保留 Live、Remix、伴奏、Pt.2、2.0 等版本信息。只有明确可等价的空白/字符格式差异才规范化，不进行歌名截断或无条件去括号。
3. 用当前歌手、专辑及经过验证的酷狗专辑提示排除冲突。数据库历史记录可以补全候选信息，但不能充当独立证据证明候选就是当前歌曲。有效非空字段冲突时不强行降级匹配。
4. 同一非零 `MixSongID` 的重复队列/历史记录去重；不同 ID 先保留。0、缺失值不作为等价标识；`TrueMixSongID` 与 `MixSongID` 不同的关系需另行验证。
5. 为每个候选建立有来源的 hash 关联：记录自身的 hash，以及该 ID 在 `MusicVersionsInfos` 中列出的资源 hash。全零、空值忽略；不因同名或时长相近把无关系的 hash 合并。特殊音效和不同剪辑保留各自时长/类型。
6. 通过这些 hash 查询 `LyricInfo`，用推荐歌词 ID 交叉验证或缩小候选，而不是跨歌曲按 ID 强行关联。路径必须局限在配置的歌词目录中，验证扩展名、文件头、解码、元数据和时间轴。
7. KRC 内部 hash、文件名 hash、数据库 hash 不同时，只有数据库关系能解释时才接受。歌词自己的总时长只能用于一致性检查，不能当作独立实测播放时长来证明歌曲身份。当前不可靠的内存时长也不能参与排歧。
8. 多个歌曲候选即使只存在一份缓存，仍保留歧义。只有所有剩余候选都经过验证地关联到同一份歌词内容，才可声明“歌词内容一致”，不能宣称已经识别了音频版本。
9. 数据库延迟、文件正在写入时有限重试；数据库与 KRC 索引按变化刷新，不每 100ms 全库解码。记录索引版本，避免刷新前后错配。无法验证的新结果不能替换为“最近听过”的猜测。
10. 结果区分已关联、歧义、等待数据库、无缓存、缓存无效；有明确无歌词依据才标为无歌词。人工选择应记录作用域，不能默认让一个标题的选择覆盖所有不同录音。

| 标题相同的版本之间切换          | 待验证专辑提示/进度复位等信号            | 身份包含专辑/其他原始字段；无法感知时明确限制     |
| 暂停、拖动、倍速                | 待专项验证                               | 不能把进度跳变一概当作切歌，也不因暂停清空身份    |
| 编辑器/客户端写入中、数据库升级 | 待兼容验证                               | 只读、完整性检查、限量重试，失败可降级            |
| 本地文件改标签、路径移动        | 待专项验证                               | 旧数据库和旧路径不视为当前事实                    |

## 社区与 API 依据

- [Microsoft SMTC 媒体属性](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssessionmediaproperties)：公开属性包括 AlbumArtist、AlbumTitle、Artist、Subtitle、Title 等，没有直接的歌曲 hash / 平台歌曲 ID。
- [KGG-Decryptor 数据库页解码实现](https://github.com/Aaron-gx/KGG-Decryptor/blob/main/tauri-app/src-tauri/src/lib.rs)：本次只借鉴数据库读取算法，未使用音频转换功能。正式引入需审查许可、来源及适用版本。
- [kugo-mcp 原生桥接快照](https://github.com/shenruyang123456/kugo-mcp/blob/e045890b322d7bfb1b57892cdfe53215c23f2124/kugo_mcp/bridge.js#L37-L51)：`SuperCall(864)` 可返回当前 hash 和 mix_song_id；本机目标版本尚未验证。上游轮询缓存策略不能直接代表底层接口实时性。

本轮未找到可直接移植、并已证明能在本机酷狗版本上无歧义完成 SMTC→数据库→KRC 的社区实现。上述本地数据库关系是本机只读实证；匹配规则和验证清单仍属于待实现建议。
