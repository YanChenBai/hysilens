# 酷狗本地歌词身份匹配调研

调研日期：2026-11-11。本文记录只读实机观察和建议，尚未改变应用匹配逻辑。数据库来自当前电脑，不能据此保证其他版本的结构或所有曲目的字段语义。

## 结论

建议优先验证“SMTC 完整元数据 → 数据库歌曲候选 → 音质 hash 关联 → LyricInfo → KRC 内容校验”。标题用于找候选，不作为最终歌曲身份。INI 是延迟写入的辅助信息；CDP 当前 hash / ID 是解决剩余歧义的可选增强来源。

仅有标题、歌手且存在多个不同录音时，数据库无法凭空恢复当前播放 ID。缓存中只有一个文件也不能排除当前播放的是另一个没有缓存的版本。

## 本机证据

数据库 `%APPDATA%/KuGou8/KGMusicV3.db` 为加密 SQLite。本次参考社区页解码算法，在内存中解码并使用 SQLite 只读查询，未修改原数据库，也未在仓库保存解码后的数据库。三份数据库快照的 `quick_check` 均通过；这不代表实时读取具有事务一致性。

相关表及用途：

| 表                      | 本次确认的相关字段                                                                                                                                        | 用途与限制                                                                             |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `PlayQueueAssistItem_0` | `SongName`, `TitleName`, `Singer`, `MusicFileAlbum`, `MixSongID`, `TrueMixSongID`, `MusicFileHash`, `OriginHash`, `LastPlayedMusicHash`, `RecommendKRCId` | 播放队列候选；不是当前播放指针，不能按最近一行或最大 ID 选歌                           |
| `MusicVersionsInfos`    | `MixSongID`, `SDHash`, `HDHash`, `PDHash`, `HiResHash`，以及各音质时长等                                                                                  | 同一记录下音质资源的关联依据；特殊音效/人声/伴奏资源应单独验证，不能一概认为时间轴相同 |
| `LyricInfo`             | `SongHash`, `KRCID`, `LyricPath`, `SongName`, `SingerNames`, `Duration`                                                                                   | 客户端记录的歌词路径；仍需检查关联和文件内容，时长可能为 0                             |
| `CompletionSongInfos`   | `MixSongID`, `Hash`, `AlbumID`, `AlbumName`, `TitleName`, `Duration`, `AudioID` 等                                                                        | 补充候选元数据；不能证明该行当前正在播放                                               |

一个包含 48 条队列记录的快照中，45 条 `LastPlayedMusicHash` 与 `MusicFileHash` 不同；其中 42 条能在对应 `MusicVersionsInfos` 行的 hash 字段中找到。记录包含重复歌曲，这不是去重歌曲数，也不是全库准确率。说明只比一个 hash 会漏掉大量本机记录，剩余 3 条不能擅自推定对应关系。

### Flower Dance 的实际歧义

| 标题                    | MixSongID   | 专辑                                                       | 数据库时长 |
| ----------------------- | ----------- | ---------------------------------------------------------- | ---------- |
| `Flower Dance`          | `104979032` | `A Cup Of Coffee`                                          | 263836 ms  |
| `Flower Dance`          | `28145635`  | `Libyus Music Sound History 2004-2010 Mixed by DJ OKAWARI` | 166974 ms  |
| `Flower Dance (花之舞)` | `170815922` | `Libyus Music Sound History 2004－2010`                    | 265848 ms  |

前两条标题和歌手相同，歌曲身份、专辑、时长不同，不能合并。第三条的 KRC 文件名和 `LyricInfo.SongHash` 使用 HD hash，KRC 内部 `[hash:]` 却使用 SD hash；`MusicVersionsInfos` 能解释这种差异，不能直接视作文件损坏。另一份 Flower Dance 的 KRC 内 `[hash:]` 为空、`[total:0]`，这些字段不能成为必填条件。

`RecommendKRCId=19525574` 出现在多条队列记录中，而本机 `LyricInfo` 中该 ID 对应 `Jamvana - OBA O`，不能把推荐歌词 ID 单独当作可靠关联键。这可能是旧值或其他客户端行为，原因尚未确认。

### SMTC 还有被当前实现忽略的信息

本次直接读取全部相关字段时得到：

```text
Title: Flower Dance (花之舞)
Artist: 空
AlbumTitle: 空
AlbumArtist: 《Libyus Music Sound History 2004－2010》
Subtitle: 空
TrackNumber / AlbumTrackCount: 0 / 0
Position / EndTime: 0 / 0
```

酷狗这次把类似专辑名的文本放在 `AlbumArtist`。当前公共采集代码只保留 `Title`、`Artist`、`AlbumTitle`，丢掉了这个线索。应先保留原始字段；只有酷狗适配器在验证格式和数据库候选后，将这种值作为专辑提示，不能全局把 AlbumArtist 当专辑名，更不能当歌手补齐。

此前连续 SMTC 采样捕获《痴心绝对 (R&B版)》、`Dancin (Krono Remix)`、`Flower Dance Pt.2`、`Flower Dance`、`Flower Dance (花之舞)`、陶喆《就是爱你》。Dancin 的 SMTC 歌手为空，仍可查到数据库歌曲和本地 KRC。Flower Dance Pt.2 首次查询没有记录、后续出现，且用户确认本来没有歌词：查不到歌词不等于歌曲识别失败。采样时间只有观察时间，没有用户点击时间，不能用来宣称端到端延迟。

## 建议的匹配规则

1. 切歌时产生新的查询代次。采集原始 SMTC 标题、歌手、专辑、AlbumArtist、Subtitle；空字段不继承上一首。标题发生变化立即撤销上一首自动匹配，异步结果必须与查询代次一致。
2. 按完整标题查数据库候选，保留 Live、Remix、伴奏、Pt.2、2.0 等版本信息。只有明确可等价的空白/字符格式差异才规范化，不进行歌名截断或无条件去括号。
3. 用当前歌手、专辑及经过验证的酷狗专辑提示排除冲突。数据库历史记录可以补全候选信息，但不能充当独立证据证明候选就是当前歌曲。有效非空字段冲突时不强行降级匹配。
4. 同一非零 `MixSongID` 的重复队列/历史记录去重；不同 ID 先保留。0、缺失值不作为等价标识；`TrueMixSongID` 与 `MixSongID` 不同的关系需另行验证。
5. 为每个候选建立有来源的 hash 关联：记录自身的 hash，以及该 ID 在 `MusicVersionsInfos` 中列出的资源 hash。全零、空值忽略；不因同名或时长相近把无关系的 hash 合并。特殊音效和不同剪辑保留各自时长/类型。
6. 通过这些 hash 查询 `LyricInfo`，用推荐歌词 ID 交叉验证或缩小候选，而不是跨歌曲按 ID 强行关联。路径必须局限在配置的歌词目录中，验证扩展名、文件头、解码、元数据和时间轴。
7. KRC 内部 hash、文件名 hash、数据库 hash 不同时，只有数据库关系能解释时才接受。歌词自己的总时长只能用于一致性检查，不能当作独立实测播放时长来证明歌曲身份。当前不可靠的内存时长也不能参与排歧。
8. 多个歌曲候选即使只存在一份缓存，仍保留歧义。只有所有剩余候选都经过验证地关联到同一份歌词内容，才可声明“歌词内容一致”，不能宣称已经识别了音频版本。
9. 数据库延迟、文件正在写入时有限重试；数据库与 KRC 索引按变化刷新，不每 100ms 全库解码。记录索引版本，避免刷新前后错配。无法验证的新结果不能替换为“最近听过”的猜测。
10. 结果区分已关联、歧义、等待数据库、无缓存、缓存无效；有明确无歌词依据才标为无歌词。人工选择应记录作用域，不能默认让一个标题的选择覆盖所有不同录音。

### 新增表与可排除的捷径

- `SongNormalHashInfos` 有 `SongHash/NormalHash/MixSongID` 字段，但本机为空，不能依赖它完成标准 hash 归一化；继续使用已观察到有效记录的 `MusicVersionsInfos`。
- `RecentlyListenSong` 有 `MixSongID/ListenDuration/PlayTime`。检查时，最新历史记录与 SMTC 当前《验伤》（卫兰，候选 `MixSongID=53304519`）不一致。它可以辅助核对历史，不能无条件取最大 PlayTime 当当前歌曲。
- `SongOperation` 有 hash、歌曲 ID、播放/下一首统计等字段；本机多条记录共享同一个日期值，不具备已确认的逐次切歌时序。
- `PlayQueueRefItem` 保存来源列表/来源歌曲引用，不是已确认的当前播放游标。
- `ShareFileItems` 保存文件路径、MD5、OriginalHash、PartMD5 等关联字段。文件资源身份与平台歌曲身份应分别记录，不能因列名含 MD5 就推断所有歌曲 hash 的计算方式。

### 同一音频对应多个歌词版本

刚才播放的《甲乙丙丁 (合唱版)》：

- SMTC：歌手只发布李佳薇；`AlbumArtist` 为 `《甲乙丙丁 (合唱版)》`，`AlbumTitle` 为空。
- 队列记录：`MixSongID=968205846`，`RecommendKRCId=844994436`。
- `LyricInfo`：同一 `SongHash=97b4c8a5a50bbd7d39740bf627c660b1` 有 `KRCID=814619243` 和 `844994436` 两份本地文件。
- 两份 KRC 均可解码，分别有 66 和 69 条时间行，时间行内容的 SHA-256 不同，不是单纯文件名不同的重复缓存。

因此，推荐歌词 ID 的合理用途是：先用歌曲身份/hash 约束到同一歌曲，再从有效歌词候选中优先选取队列推荐 ID。若推荐 ID 指向别的歌曲、文件损坏或不存在，则不能强行采用；也不能无依据选择“最新文件”。这补充了前面的推荐 ID 冲突规则。

另一次 SMTC 读取《验伤》时，歌手为卫兰、`AlbumArtist=《验伤》`、`AlbumTitle` 仍为空。专辑提示并非只在 Flower Dance 上出现，但它仍是酷狗本机观察到的非标准字段使用方式，需要按来源限定并保留原值。

本轮没有找到已经验证比 INI 更实时的磁盘播放游标。当前最直接的改进仍是完整采集 SMTC 字段，结合数据库歌曲身份、音质映射和受身份约束的歌词版本选择；强歧义需要额外实时 ID/hash 来源。

## AOB 动态入口定位的初步验证

最终读取优先级为：当前对象的内存歌词 → 内存歌曲 hash/ID → 数据库与本地 KRC → SMTC 与数据库匹配 → 缓存匹配/人工选择。当前研究顺序按用户最新要求调整为：先完成内存 hash/ID，内存歌词最后研究。

本机只读初步扫描已发现《验伤》的 UTF-16 歌词行片段及歌曲 hash 多份副本，但尚未找到经过验证的完整歌词容器、时间轴和稳定所有权关系。发现字符串不能作为运行时匹配成功的依据。

针对本机模块文件的可执行代码节，检查已知入口的 RIP 相对寻址引用后：

- `kgplayer.dll 1.2.0.523` 中一个带通配位的代码特征唯一命中，解析其指令位移可反推出已知进度 RVA `0x3949F8`。这只证明该文件上的候选特征可用，尚未验证其他构建或集成到采集逻辑。
- `kugou.dll 20.1.61.28014` 中引用 `0x2434B30` 的单例访问器代码，初版通配特征命中 6 个不同入口，不能直接取第一项。简单的 RTTI 检查本次也没有取得可用于排歧的对象类型名。
- 已知时长根地址可以动态找到，不代表根对象内的时长字段偏移正确；AOB 不能修复此前两条时长链误读其他字段的问题。

后续定位应限制模块/代码节，屏蔽会变化的 RIP 位移和调用位移，解析指令得到真实入口。入口唯一性、对象边界、歌词行/字时间轴以及切歌后的所有权都需验证；零命中或多命中时拒绝该路线。只在进程连接或校验失效时受限重扫，不在每帧扫描整个进程。歌词对象解码仍需要按已确认结构维护，不能仅凭 AOB 命中绕过版本适用范围。

## 2026-11-12：当前条目 ID 与内存 hash 的只读验证

以下是接入采集器前，本机 `kugou.dll 20.1.61.28014` 的研究记录；最新实现范围见文末。使用 `ReadProcessMemory` 读取，没有调用目标进程函数、注入代码或修改播放器内存。模块基址和堆地址来自当前进程，不能跨进程复用绝对地址。

### 从客户端状态代码找到当前条目

从序列化 `progress/play_status/QueueSource` 的原生函数追踪，找到其使用的当前队列条目，而不是从全进程扫描结果中挑选一个 hash。

```text
manager = ptr(kugou.dll + 0x2436958)
impl = ptr(manager + 0x20)
queueState = ptr(impl + 0x70)
locator = queueState + 0xC8       // 内联结构，不再解引用
```

`locator` 本机布局为：`i32 queueItemId`、`i32 listId`、`u64 listInterface`。本次 `listId=0`，接口虚表第 `+0x8` 个字节位置的函数返回常量 6。它对应本次观察到的 `PlayQueueAssistItem_0` 来源。这里的 `queueItemId` 是队列 `SongID`，不是 `MixSongID`，两者不能混用。

原生代码会通过列表接口虚表 `+0x138` 查找当前歌曲。研究脚本只还原其读数据路径，没有从外部执行该接口。队列引用树取得的四个整数依次为队列条目 ID、来源类型、来源列表 ID、来源歌曲 ID；本次观察到它们形如 `[10219, 6, 0, 10219]`。后续需要按来源类型分支，不能把所有来源强制当作同一张表。

另一个播放对象可经 `impl+0x160` 找到；沿其接口追踪得到的队列 `+0x78` 条目曾停留在上一首（10216），此时 `+0xC8` 已为当前 10217。原生状态代码也只在正常歌曲信息获取失败后使用这一备用路径。它尚不具备可靠的兜底条件，不能遇到读取失败就接收其非零 ID。

### AOB 定位身份入口

简单单例访问器特征存在多个命中，不能取第一项。改用原生状态序列化器的调用上下文：

- 本机调用位置 RVA `0x10026A3`，62 字节模式，屏蔽其中相对调用/跳转位移；在模块文件可执行节中唯一命中。
- 跟随第一条 `E8` 到中转函数，再跟随 `E9` 到单例 getter（本机 RVA `0x145B954`）。
- getter 前有 `40 53` 前缀；其 `48 8B 05` 的位移位于 getter `+9`，指令结束在 `+13`。按有符号 RIP 相对位移解析得到根槽 RVA `0x2436958`。
- 对当前进程中的调用位置也做了同一带通配模式校验，匹配通过。

这验证的是身份入口，区别于此前的时长入口 `0x2434B30`。本次没有验证重启、ASLR 后重新连接或其他客户端构建。AOB 可以动态求入口，但不使后续结构偏移自动兼容所有版本；零命中、多命中、目标越界或对象校验失败时，应放弃此路线。

### 从条目找到歌曲缓存记录

本机来源 6 对应内部来源选择器 7，原生 provider 查表路径最终取得：

```text
sourceInterface = ptr(ptr(impl + 0x110) + 0x40)
cacheManager = ptr(sourceInterface + 0x10)
lists = ptr(cacheManager + 0x40)
```

`sourceInterface` 虚表 `+0x138` 本机指向 RVA `0xF26A88`，继续进入 `0xF6CC50 → 0xF6CE48`。列表索引是一个树：头结点为 `ptr(lists+0x40)`，根为 `ptr(head+8)`，节点的键在 `+0x20`，左右子树为 `+0` / `+0x10`，空结点标志在 `+0x19`，列表对象指针在 `+0x28`。本次按列表 ID 0 命中。

歌曲缓存树由原生 `0xF6CDC4 → 0xFD228` 查找：

```text
owner = ptr(listObject + 0x38)
head = ptr(owner + 8)
rootHook = ptr(head + 0xD0) & ~1
node = rootHook ? rootHook - 0xD0 : 0
record = ptr(node)
key = i32(record)
```

节点左右链接在 `+0xD8` / `+0xE0`，非零链接减 `0xD0` 得到对应节点。它与队列引用树的 hook 偏移不同，不能复用队列树的 `0x10/0x18/0x20` 布局。研究读取设置了步数上限、重复节点检查，并校验最终记录 ID。树的并发修改仍需在正式实现中处理为可重试失败。

命中的歌曲记录中，本次确认的字段如下（小端）：

| 偏移     | 类型          | 对应数据库字段        |
| -------- | ------------- | --------------------- |
| `+0x00`  | i32           | 来源歌曲条目 ID       |
| `+0x38`  | 16 字节二进制 | `MusicFileHash`       |
| `+0x280` | u32           | `RecommendKRCId`      |
| `+0x298` | u64           | `MixSongID`           |
| `+0x430` | 16 字节二进制 | `LastPlayedMusicHash` |

hash 的 16 字节按原字节顺序转为 32 位十六进制文本，不能当作 32 字节 ASCII，也不能倒转整个 MD5。这里是直接读取客户端保存的资源身份，并未重新计算音频 hash。两份 hash 可能相同，也可能因音质不同而不同，不能固定只读一份。

### 已完成的交叉核对与未完成边界

100ms 采样的当前条目监听依次观察到：

| 队列 ID | 数据库核对标题                                                 |
| ------- | -------------------------------------------------------------- |
| 10217   | 大头针 Official、雅雯 - 回到我们的故事里 (r&b)                 |
| 10218   | 谢尔西 - 你怎么舍得我难过 (烟嗓版)                             |
| 10219   | 张云羡、ProdbyMend - 海屿你                                    |
| 10220   | 二宮愛 - Swimming Baby (English Version)                       |
| 10221   | DJ OKAWARI、二宮愛 - SPEED OF LIGHT (2025明日方舟音律联觉现场) |

后两首还直接监听了歌曲记录中的两份 hash 与 `MixSongID`，均与数据库快照吻合：

- 10220：`11f2ab9db30fda31426862de71ac9f96` / `ef9c21727438f0922b9a1035551c72e9`，`MixSongID=640500979`。
- 10221：两份均为 `3da20dbf0c31804e194e0e477bb2c14f`，`MixSongID=800812472`。

另对数据库快照中的 37 条队列记录逐个按 ID 查内存歌曲缓存：37 条均命中，两份 hash、MixSongID 和推荐歌词 ID 四项均 37/37 一致，其中 33 条推荐歌词 ID 非零。这支持本机字段布局判断，但不是 37 次播放切换测试。

10221 的数据库快照没有歌词候选；这只表示该快照未关联到 KRC，不能从标题类似或上一首有歌词推导它有可用歌词，也不能宣布该歌曲永远无歌词。

内存切换与 SMTC 采样相互吻合；10220 的内存事件比 SMTC 观察值早约 176ms，10221 的内存事件早约 66ms。它们只是两个独立轮询器的观察时间差，没有记录人工点击时刻，不能据此保证切歌延迟。10221 的 SMTC 歌手还先后从单人更新到双人，进一步说明不能在单次标题/歌手更新时认定元数据已完整。

正式集成前仍需覆盖：重启后重新定位、其他来源列表/本地歌曲、客户端重建缓存、快速 A→B→A、暂停/拖动、音质切换、数据库尚未落盘及当前条目和实际音频短暂不同步。研究脚本每轮重新定位记录，读后重查当前 ID，状态比较同时包含两份 hash 和 MixSongID；这些检查减少错配，但尚不能声称解决所有并发边界。

下一步可用直接读取的 hash/MixSongID 约束数据库，再用受歌曲身份约束的 `RecommendKRCId` 选择歌词版本。内存身份可独立于数据库读取；数据库仍用于关联本地 KRC。没有数据库记录、没有有效文件或出现强歧义时应明确缺失并降级，不继承上一首歌词。内存歌词对象研究继续后置。

## 首轮内存身份接入

本轮已在 Rust 采集器中接通“内存 hash/ID → 本地 KRC 文件名中的 hash/歌词 ID”。本地数据库解密及跨音质/异名路径关联仍未接入运行时；内存歌词继续后置。

- 只支持已验证的 x64 `kugou.dll 20.1.61.28014`，当前队列/引用来源类型 6、列表 0。其他来源或未知结构明确返回身份错误并使用原有匹配路径。
- 每次连接只在模块可执行节内受限扫描 AOB，最多 64 MiB；唯一命中并校验调用/getter 后，动态求出单例根槽。之后每帧从当前游标重新找引用和歌曲记录，不缓存堆记录地址；树遍历最多 128 步，并拒绝循环。
- 复读当前游标与两次完整身份，失败不保留上一帧的 hash。歌曲身份及读取错误只进入酷狗专用诊断报告，不影响有效进度。公共播放协议仅保留通用 `trackId`，缓存匹配使用不序列化的内部 hash 与歌词 ID 提示。模块入口定位结果及每次身份读取也进入诊断报告。
- 同时接受 `MusicFileHash` 和 `LastPlayedMusicHash`，全零 hash 不参与匹配。先用 hash 约束到本地已成功解码的 KRC，再在这些候选内用 `RecommendKRCId` 优选。ID 相同但 hash 不同的文件被排除；多份不同歌词仍有歧义时不按目录顺序猜测。
- 已读到有效内存 hash 却没有对应 KRC 时，状态为 `missing`，不再回退到同名其他录音；内存身份不可用时保留旧标题/歌手匹配。用户手动选择仍可覆盖自动匹配。
- 以队列 ID、来源 ID、MixSongID 和两份 hash 组成 `trackId`。相同标题下切换不同条目也会递增会话代次并清空旧手选；同一身份的 SMTC 歌手稍后补全不重置手选。推荐歌词 ID 更新会重做自动匹配，但不作为一次切歌。

Rust 只读实测读取了已运行播放器的条目 10225；随后条目 10237 的内存身份对应陶喆《普通朋友》，本地唯一匹配文件为 `陶喆 - 普通朋友-90c14c522322ccce47be061ad7cbc745-320659356-00000000.krc`，返回 `matchedMemoryHash`，缓存解析问题数为 0。整个实测未启动应用/服务器，也未操控播放器。

可手动执行只读探测（默认测试会跳过此项，播放器需已运行）：

```powershell
cargo test -p hysilens-core inspect_running_kugou_identity -- --ignored --nocapture
```

若显式设置 `HYSILENS_KUGOU_PROBE_CACHE` 为本地歌词目录，探测还会输出 KRC 匹配状态、候选数量和选中文件名。它不加载数据库，也不导出歌词正文。

此次接入不代表重启、其他电脑或所有来源已经验证。用户仍需手动验证界面中的切歌、同名版本、无歌词歌曲、快速切换和跨客户端重启；失败时可通过诊断报告比较身份入口、内存字段与实际会话。
