# 酷狗进度采集备用方案

调研日期：2026-11-11。本文记录候选方案和验证顺序，除双时长链外，其余备用通道尚未集成，也未在本项目中实机验证。

## 当前依据

异常电脑的旧报告显示：三份文件的版本与本机 SHA-256 相同，长链读出的原始时长始终为 `528`，进度在约一秒的采集区间内不变。用户反馈界面短暂显示后报错。可以确认长链采样不满足时间轴校验；不能仅凭这个报告确认进度地址正确或错误。

当前已实现：`20.1.61.28014` 优先尝试 `0x108 → 0x8C`，失败后尝试 `0x130 → 0x130 → 0x2A4`。新诊断格式为 v2，包含两条链、13 次采样、SMTC 和应用实际会话状态。

## 方案与优先级

| 路线                   | 社区依据                                   | 本项目状态与适用条件                                                   |
| ---------------------- | ------------------------------------------ | ---------------------------------------------------------------------- |
| 双时长链内存读取       | AF Media Bar 对同版本使用短链              | 已实现，优先使用；仍需跨歌曲、启动和电脑验证                           |
| SMTC 时间轴            | 已有媒体会话通道；社区报告过酷狗时间轴为零 | 用新报告判断具体客户端是否确实提供有效数据，不能只看歌名正常就判定可用 |
| CDP + 酷狗原生网页桥接 | kugo-mcp 有进度与时长读取源码              | 最值得验证的新通道，不依赖 DLL 固定偏移；当前版本兼容性与延迟待确认    |
| 手动校准 + 本地计时    | Lyricify Lite 旧版文档说明了计时降级       | 仅作为用户明确启用的近似模式；拖动进度和中途连接需要重新校准           |

## 1. 继续保留内存通道

AF Media Bar 在固定版本源码中，将 `kgplayer.dll 1.2.0.523` / `kugou.dll 20.1.61.28014` 对应到进度偏移 `0x3949F8`、时长入口 `0x2434B30`、时长链 `0x108 → 0x8C`、每秒 1000 单位。

来源：[KuGou.cs，8e0564f](https://github.com/Fervent-Tempo/AF-Media-Bar/blob/8e0564f91e10541eed321681ddf72da024e3fa6f/src/AFMediaBar/Classes/Services/Media/Sources/KuGou/KuGou.cs#L27-L34)。同文件还读取 DirectShow 对象判断播放/暂停；该状态读取不是独立的进度接口，不能单独替换失效的进度地址。

建议：先分析新版报告，分别检查进度是否随真实播放推进、短链时长是否对应歌曲、两条链在切歌后是否变化。只在某一时刻读通，不足以证明长期可靠。

## 2. CDP 原生桥接候选

`shenruyang123456/kugo-mcp` 通过本机 CDP 连接酷狗内嵌页面，调用 `external.SuperCall(864, ...)`，在同一回调中取得 `hash`、`filename`、`play_status`、`duration` 和 `progress`。

来源：[bridge.js](https://github.com/shenruyang123456/kugo-mcp/blob/e045890b322d7bfb1b57892cdfe53215c23f2124/kugo_mcp/bridge.js#L37-L51)。上游将 `progress / 10000` 解释为毫秒并检查与时长的关系，移植前仍须验证本项目目标版本的单位：[native.py](https://github.com/shenruyang123456/kugo-mcp/blob/e045890b322d7bfb1b57892cdfe53215c23f2124/kugo_mcp/native.py)。许可为 MIT。

连接条件：客户端需提供本机调试端口，且存在可连接的推荐/搜索内嵌页面。普通方式启动的单实例酷狗可能忽略调试参数，需要用户完整退出后以相应方式启动。依据：[上游 README](https://github.com/shenruyang123456/kugo-mcp/blob/e045890b322d7bfb1b57892cdfe53215c23f2124/README.md#L41-L52)。这里仅作方案记录，不自动重启酷狗或更改其启动配置。

限制：上游读取有 4.4 秒间隔、6 秒过期阈值，并在用户操作客户端时延后请求、出错时退避。这意味着适合借鉴数据通道，不能把其轮询策略直接当作已经验证的逐字歌词同步策略。依据：[playback.py](https://github.com/shenruyang123456/kugo-mcp/blob/e045890b322d7bfb1b57892cdfe53215c23f2124/kugo_mcp/playback.py#L7-L8)。

上游验收记录说明了已有客户端连接与信息读取成功，也明确保留长期稳定性和跨版本验证：[VALIDATION.md](https://github.com/shenruyang123456/kugo-mcp/blob/e045890b322d7bfb1b57892cdfe53215c23f2124/VALIDATION.md)。没有证据证明该通道已适配本项目使用的 `20.1.61.28014`。

工程判断：先做只读、按需的原生快照验证，比较页面桥接数据与播放器显示；确认后再评估本地平滑计时、短周期校准以及拖动后的恢复延迟。正式集成可以直接在 Rust 实现 CDP 客户端，不必要求用户部署整套 Python/Node MCP；这属于待设计方案，不是现成功能。

## 3. SMTC 和近似计时的边界

AF Media Bar 的 [Issue #270](https://github.com/Fervent-Tempo/AF-Media-Bar/issues/270) 记录了酷狗只提供标题/歌手、进度与时长均为零的环境。对当前电脑必须以实际采样为准。

Lyricify Lite 的旧版官方说明将酷狗列为无 SMTC 时间轴，并说明内置定时器无法感知手动跳转：[旧版使用指南](https://github.com/Lyricify/Lyricify/blob/main/docs/Lyricify%20Lite/README.md)。该页已注明迁移且不再维护，不能用它断言所有当前酷狗版本都无时间轴；新文档本次访问返回 403。

近似模式应让用户手动指定当前时间或以某行歌词为锚点，再按播放/暂停状态计时。必须显示为近似同步，中途连接、拖动、切歌及倍速变化都需要校准。不能把零位置加墙钟时间当作精确进度。

## 下一轮验证

1. 使用当前 EXE 在异常电脑采集 v2 报告。保持播放，关注 `mediaBefore` / `mediaAfter` 的状态、原始时间戳和位置，不只看外推位置。
2. 比较两条链的原始时长、`timeline` 校验结果和 `preferredUsableLayoutIndex`。短链失败、长链成功的场景也要保留。
3. 在歌曲中途暂停、恢复、拖动后分别导出；换两首不同时长的歌曲，再重启酷狗复测。
4. 两条链均失败且 SMTC 不可用时，优先验证 CDP 原生快照，记录歌名/hash、时长、进度、调用耗时和错误；不先接入高频自动轮询。
5. 桥接在该版本验证可用后，再决定是整体切换来源，还是仅在内存通道失败时启用。不同通道混用时，必须先验证歌曲身份、单位和采样时间一致。

本次没有找到经过确认、可直接用于 Windows 酷狗当前版本的 UI Automation 进度读取或公开稳定的播放进度 SDK。在线音乐 API 的歌曲时长和歌词时间戳也不等于本地客户端的实时播放位置。
